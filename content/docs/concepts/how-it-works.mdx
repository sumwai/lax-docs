---
title: 工作原理
description: 供应商、账号、模型目录、可达性与请求转发之间的关系
---

lax 的核心数据只有几层：供应商定义“往哪里发”，账号保存“以谁的凭据发”，模型目录与可达性共同回答“这个账号能不能用这个模型”，选号策略决定“多个账号里先试哪个”。

## 五个对象

| 对象 | 回答的问题 | 命令 |
| --- | --- | --- |
| 供应商 | 这家上游的地址、路由与默认协议是什么 | `lax provider` |
| 账号 | 用哪份凭据、属于哪家供应商、优先级多少 | `lax account` |
| 模型目录 | 上游曾公布过哪些模型，元数据与价格是什么 | `lax model sync`、`lax model add` |
| 可达性 | 某个账号上的某个模型是否探活通过 | `lax model probe`、`lax model add` |
| 选号策略 | 同一模型有多个账号时按什么顺序尝试 | `lax route` |

## 数据流

```text
客户端请求
   │  按路径确定入站协议
   ▼
解析模型名（先查别名）
   │
   ▼
筛出声明提供该模型的账号
   │  排除停用、冷却、无该模型的账号
   ▼
按选号策略排序
   │
   ▼
逐个尝试：拼地址、注入凭据、转换协议
   │
   ├─ 成功 → 写请求记录与选号统计 → 返回客户端
   └─ 失败 → 按失败类型冷却该账号的这个模型 → 试下一个
```

## 供应商与账号分离

供应商保存公共事实：base URL、每条协议的路由、默认协议、凭据头写法与模型列表覆盖。账号只保存凭据、供应商名、优先级与启用状态。

这样做的结果：

- 同一家供应商的多个账号共享地址与路由，不必重复填写。
- 换 key 用 `account set`，不删号、不丢探活结果与历史记录。
- 一个账号只属于一家供应商；同一家上游要分多个账号时，新建多个账号指向同一供应商。

## 模型目录与可达性分开

模型目录记录“上游有什么”，可达性记录“这个账号上的这个模型现在能不能用”。

| 动作 | 写模型目录 | 写可达性 | 消耗 token |
| --- | --- | --- | --- |
| `model sync` | 新名字补行，已有行只补非空元数据 | 把这些名字标为 `allowed` | 否 |
| `model probe` | 补协议与元数据 | 按真实请求结果改写 | 是 |
| `model add` | 新名字补行，已有行不动 | 写 `allowed` 与可选协议 | 否 |

`model sync` 只做加法：它不删除行，也不会把探活已经判定为 `forbidden` 或 `missing` 的行翻回可用。只有真实探活或手工声明才改可达性。因此“同步过”不等于“能用”。

## 有效协议怎么定

一个模型在某个账号上的有效出站协议按以下顺序确定：

1. 账号级协议覆盖（`account_models.protocol`，由探活或 `model add --protocol` 写入）。
2. 模型目录声明的协议集合里，若包含供应商的有效默认协议，就用它。
3. 否则在集合里按 `openai-chat` → `openai-responses` → `anthropic` → `gemini` 的顺序取第一个。
4. 集合为空时回退到供应商的有效默认协议。

有效默认协议本身也有顺序：显式声明的 `default_protocol` 优先，其次取已经声明的路由，最后按 `openai-chat` → `openai-responses` → `anthropic` 回退。gemini、systemone、embeddings、speech、transcriptions 不会自动成为默认协议，必须显式指定。

## 一次请求的边界

- 只有 `gateway` 包会发上游请求；CLI 的 `model call`、`model decide`、`model speak` 与 `model transcribe` 会在本进程起一个临时网关再打进去，因此走的也是同一条路径。
- 入站与有效出站协议相同且属于宿主直通协议时，报文原样转发；不同时经中间表示转换。systemone、embeddings 与语音协议不参与对话协议的转换。
- 一次客户端请求可能尝试多个账号，每次尝试各写一条请求记录。客户端看到的是一个响应，账单里可能有多条失败记录。
