---
title: 失败处理
description: 用规则决定上游失败后的重试、冷却、停用与换号
---

上游返回错误时，网关默认按状态码处理：401 停用账号，403 与普通 400 原样返回，429、408、5xx 与连接层失败先冷却这个账号-模型，再换下一个候选。冷却指在一段时间内不再把这个账号或账号-模型放进候选。

这套默认处理不看响应正文。余额不足、套餐到期这类失败常用 400 返回，网关会把它当成客户端写错了请求：不重试、不冷却、不停用，也不记入选号统计。同一个会话会继续粘在这台已经不能用的账号上。

`route policy` 把这段处理变成可配置的规则。一条规则由条件与动作组成：条件决定什么时候命中，动作决定命中后做什么。规则存在数据库里，改完立即生效，不需要重启。

## 条件

条件之间是「并且」，同一个条件里的多个值是「或者」。

| 条件 | 写法 | 说明 |
| --- | --- | --- |
| 账号 | `--account <账号>` | 只匹配一个账号 |
| 供应商 | `--provider <供应商>` | 只匹配一家供应商 |
| 模型 | `--model <模型>` | 只匹配一个模型，支持别名 |
| 状态码 | `--status 400,429,5xx` | 400–599 的具体码，或 `4xx`、`5xx`；可以逗号分隔，也可以重复写 |
| 错误文本 | `--error-contains "insufficient credits"` | 大小写不敏感的子串；可以重复写，任意一条命中即可 |
| 错误正则 | `--error-regex "<正则>"` | Go 正则，最长 512 字符 |
| 全部错误 | `--all-errors` | 在其余条件划定的范围内匹配任何状态与错误文本 |

错误文本取网关已经脱敏并截断到 300 字符之后的内容。

没有写 `--status`、`--error-contains`、`--error-regex` 的规则必须显式带 `--all-errors`，否则命令拒绝写入。`--all-errors` 不能和这三项同时出现。这条限制防的是漏写条件后把正常的 400 也当成账号故障。

## 动作

动作直接写在参数上，没有单独的动作名。

| 动作 | 写法 | 说明 |
| --- | --- | --- |
| 重试 | `--retry N` | 同一账号同一模型再试 N 次，N 为 1–10，总调用 N+1 次 |
| 重试间隔 | `--retry-base 时长` | 第一次等待，默认 500ms，范围 100ms–10s |
| 冷却 | `--cooldown 时长` | 冷却 1 秒到 30 天；带 `--model` 只冷却账号-模型，不带则冷却整个账号 |
| 停用 | `--disable` | 永久停用整个账号，需要手工 `lax account enable` 恢复 |
| 换号 | `--next_route` | 处理完重试与状态动作后，换下一个候选账号 |
| 返回 | `--return` | 把上游错误返回客户端 |

规则是整条替换：命中的规则定义这次失败的全部行为，没写的动作不做。

`--disable` 与 `--cooldown` 互斥，`--next_route` 与 `--return` 互斥。两个流程都不写时默认 `--return`。至少要有一个动作。

重试的等待从 `--retry-base` 开始翻倍：第 i 次等待 `min(base × 2^(i-1), 8s)`。一个客户端请求在一个候选账号上累计最多等待 60 秒，客户端断开就停止。

每次重试都是真实的上游调用，各写一条请求记录。

已经开始向客户端写响应字节的请求不会重试，也不会换号。

## 匹配顺序

用户规则按 `priority` 升序匹配，`priority` 相同按 id 升序，第一条命中的规则生效。用户规则都没命中时，再匹配代码里的内置兜底：

| 内置规则 | 动作 |
| --- | --- |
| 401 | 停用账号，返回 |
| 402 | 停用账号，换号 |
| 400 或 403 且错误文本命中计费关键词 | 停用账号，换号 |

计费关键词只有 `insufficient credit`、`no credits`、`out of credits`、`credit balance`、`purchase more credits`、`payment required`、`insufficient_quota`、`余额不足`、`欠费`、`额度不足`、`额度已用完`、`充值`。裸 `credit` 与裸 `quota` 故意不算关键词，它们会命中无关的报错。

所有规则都没命中时，按本文开头的默认处理执行。

## 冷却范围与选号

选号指网关为一次请求挑账号。`--cooldown` 带 `--model` 时写这个账号-模型的冷却，只影响这一个模型。不带 `--model` 时写账号级冷却，这个账号的所有模型一起退出候选。

账号级冷却与账号-模型冷却分开存放，互不影响。

账号级冷却会进入选号的硬过滤。硬过滤指在排序之前直接排除不满足条件的账号，候选按顺序排除四类账号：已停用、账号在冷却中、没有声明这个模型、这个模型在冷却中。`lax route explain` 会列出被排除的账号与原因，账号级冷却写「账号冷却中」。

`--disable` 永远停用整个账号，与规则有没有带 `--model` 无关。

## 命令

```bash
lax route policy ls [--all] [--json]
lax route policy show <id> [--json]
lax route policy add [条件] [动作]
lax route policy set <id> [字段 ...]
lax route policy unset <id> <字段开关 ...>
lax route policy rm <id>
lax route policy enable <id>
lax route policy disable <id>
lax route policy test --status <码> [--message <文本>] [--explain]
```

`ls` 按生效顺序列出用户规则，再列内置兜底；`--all` 把停用的规则也列出来。

`set` 只改显式给出的字段。`unset` 用开关清掉指定字段；清掉最后一个条件时必须同时带 `--all-errors`。

`rm` 只能删用户规则，内置兜底删不掉。

`test` 只按给定事实做匹配，不请求上游、不写数据库。加 `--explain` 会逐条列出命中或跳过的原因。

## 示例

```bash
# 5xx 与 429：同一账号重试一次（等 500ms），然后返回
lax route policy add --provider commandcode --status 5xx,429 --retry 1

# 余额不足：停用整个账号并换号
lax route policy add --account acct-a --status 400 \
  --error-contains "insufficient credits" --disable --next_route

# 某个模型的 5xx：只冷却这个账号-模型 30 分钟，然后换号
lax route policy add --model glm-4.6 --status 5xx --cooldown 30m --next_route

# 只预演匹配
lax route policy test --status 400 --message "You have insufficient credits" \
  --provider commandcode --explain
```

`--cooldown` 按整秒存储，30 天写成 `720h`。

## 探活

探活是向一个账号发一条最小请求，判断它能不能用。`lax account test` 与语音的应错探活会先跑同一批规则。

计费类 400 命中停用或冷却规则时，账号不会被标成可用。只带换号或返回的规则不改账号状态。

命中规则时，`account test` 的输出会多一行「命中策略」，`--json` 多 `policy` 与 `policy_action` 两个字段。

`lax model probe` 的普通对话探活仍是模型级判断，不按规则停用或冷却账号。
