lax 的版本号来自 `v*` tag，构建时注入二进制。发布包由 GitHub Actions 生成，正式 tag 还会自动部署到生产主机。

## 版本号

```bash
lax version
lax version --json
```

输出格式：

- 发布包：`lax 0.2.1`；
- 源码构建：`lax 0.2.1-3-gabc1234`，表示 tag 之后还有三个提交；
- 未打 tag 的直接 `go build`：`lax 0.1.0-dev`。

版本号不在源码里手工改。构建时通过 `-X lax/internal/cli.version=<版本>` 注入，`make build` 用 `git describe --tags --match 'v*'` 推导。

## 升级步骤

1. 下载对应平台的新发布包与 `checksums.txt`；
2. 核对 SHA-256；
3. 运行 `./lax version`，确认与 tag 一致；
4. 停掉 `serve`；
5. 备份配置、数据库、密钥与插件目录；
6. 替换 `lax` 二进制；
7. 运行 `lax doctor`；
8. 启动 `serve`；
9. 用 `lax model call` 或客户端验证一条请求。

数据库结构由程序自动迁移。升级前备份仍是必要步骤，尤其是跨多个 MINOR 版本时。

## 预发布 tag

带 `-` 的 tag 是预发布，例如 `v0.3.0-rc.1`：

- 会创建 GitHub Release；
- 不会自动部署到生产主机；
- 手动安装时同样可以核对 `lax version`。

正式 tag 才会触发部署。部署只替换二进制，不改配置、数据目录与 systemd unit。

## 自动部署

生产部署由 Release 工作流完成：

1. 下载 Linux amd64 包与 `checksums.txt`；
2. 校验 SHA-256；
3. 通过 SSH 上传；
4. 核对包内 `lax version` 与 tag 一致；
5. 原子替换 `~/.local/bin/lax`；
6. 重启 `lax.service`；
7. 轮询 `http://127.0.0.1:4567/healthz`；
8. 30 秒内不通过就回滚到 `~/deploy/lax.previous`。

工作流重跑时，同 tag 的 Release 会复用已有产物，不覆盖已发布资产。

## 回滚

自动部署失败时会回滚二进制。手动回滚：

```bash
cp ~/deploy/lax.previous ~/.local/bin/lax
systemctl --user restart lax.service
```

数据库迁移通常只向前。跨大版本回滚前先备份，并确认旧版本能打开新结构；不能时用升级前的数据库备份恢复。

## 发版规则

- 语义化版本：`vMAJOR.MINOR.PATCH`；
- 1.0 之前，破坏性改动升 MINOR，其余升 PATCH；
- 已推送的 tag 不移动、不删除、不重打；
- 发错了就发新的 PATCH 版本；
- 发版前工作区干净，`make check` 通过；
- 本地先 `make dist VERSION=vX.Y.Z` 验证四个发布包与 `dist/checksums.txt`，再打 annotated tag。
