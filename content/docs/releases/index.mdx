版本号的事实来源是 `v*` tag。源码里的 `0.1.0-dev` 只是未注入版本号时的默认值。

## 规则

| 项 | 规则 |
| --- | --- |
| 版本格式 | SemVer：`vMAJOR.MINOR.PATCH` |
| 1.0 之前 | 破坏性改动升 MINOR，其余升 PATCH |
| tag 类型 | annotated tag，例如 `git tag -a v0.2.1 -m "lax v0.2.1"` |
| 已推送 tag | 不移动、不删除、不重打 |
| 发错版本 | 发新的 PATCH |

只有 `v*` tag 参与版本推导。`backup-*` 是本地备份标记，不参与发布。

## 版本号注入

构建时通过链接参数写入：

```bash
-X lax/internal/cli.version=<版本>
```

`make build` 使用：

```bash
git describe --tags --match 'v*' --always --dirty
```

去掉前缀 `v` 后作为版本号。tag 之后还有提交时会带上提交数与哈希，例如 `0.2.1-3-gabc1234`。

## 发布流程

1. 确认工作区干净；
2. 运行 `make check`；
3. 本地验证发布包：

```bash
make dist VERSION=v0.2.2
ls dist/
cat dist/checksums.txt
```

4. 打 annotated tag；
5. 推送 `master` 与 tag；
6. 等待 GitHub Actions 创建 Release；
7. 下载产物，核对 `checksums.txt` 与 `lax version`。

```bash
git tag -a v0.2.2 -m "lax v0.2.2"
git push origin master v0.2.2
```

## 发布包

`make dist` 生成四个平台包：

| 平台 | 架构 |
| --- | --- |
| Linux | amd64、arm64 |
| macOS | amd64、arm64 |

外加 `dist/checksums.txt`。Windows 不在发布范围：`serve` 与 `plugin reload` 依赖 Unix 信号。

## 自动化

| 工作流 | 触发 | 动作 |
| --- | --- | --- |
| `.github/workflows/ci.yml` | `master` 与 pull request | 运行 `make check` |
| `.github/workflows/release.yml` | 推送 `v*` tag | 构建发布包、创建 GitHub Release、正式 tag 自动部署 |

正式 tag 指不带 `-` 的版本。`v0.3.0-rc.1` 这类预发布 tag 会建 Release，但不部署生产。

## 生产部署

Release 成功后，`deploy` job：

1. 下载 Linux amd64 包与 `checksums.txt`；
2. 校验 SHA-256；
3. 上传到生产主机；
4. 核对包内 `lax version` 与 tag；
5. 原子替换 `~/.local/bin/lax`；
6. 重启 `lax.service`；
7. 轮询本机 `/healthz`；
8. 30 秒内不通过就回滚到 `~/deploy/lax.previous`。

部署只替换二进制，不改配置、数据库、密钥与 systemd unit。
