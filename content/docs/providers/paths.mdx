供应商的每条路由是一段地址：相对路径拼在 base URL 之后，整条地址直接使用。两种写法可以写在同一家供应商的不同协议上。

## 路径写法与规整

| 写法 | 例子 | 转发时 |
| --- | --- | --- |
| 相对路径 | `/v1/chat/completions` | 拼在 `--base-url` 之后 |
| 整条地址（含 `://`） | `https://openai.example.com/v1/chat/completions` | 直接使用，不再拼 `--base-url` |

两种写法都先规整再入库，所以照着上游文档抄来的斜杠写法不会变成两条不同的地址：

| `--openai` 的取值 | 落库值 |
| --- | --- |
| `v1/chat/completions` | `/v1/chat/completions` |
| `//v1//chat/completions` | `/v1/chat/completions` |
| `/v1/chat/completions/` | `/v1/chat/completions` |
| `https://API.Example.com//v1//chat/completions/` | `https://API.Example.com/v1/chat/completions` |
| `https://api.example.com//v1//chat/completions/?next=//a//b` | `https://api.example.com/v1/chat/completions?next=//a//b` |

规整只落在路径上：连续斜杠合并成一个、去掉末尾斜杠、相对路径补一个前导斜杠。整条地址的 scheme 归一为小写，其余部分一个字不动：主机名大小写、端口、授权信息、查询串与 `#` 之后的内容。

`https://`（没有主机名）、`ftp://host/x`（scheme 不是 http 或 https）属于用法错误，当场拒绝。

把 `myco` 的两条路由换到别的域名，就是把这两个 flag 的取值从相对路径改成整条地址：

```bash
lax provider set myco \
    --openai https://openai.example.com/v1/chat/completions \   # [!code highlight]
    --anthropic https://claude.example.com/v1/messages          # [!code highlight]
```

`--models-path` 是供应商级覆盖，取值同样支持相对路径与整条地址，优先级见[模型列表地址的取值顺序](/docs/providers#模型列表地址的取值顺序)。

## 会被拒绝的写法

| 情况 | 结果 |
| --- | --- |
| 名称已存在 | 报错并提示改用 `provider set` |
| 一条协议路由都没声明 | 用法错误：至少给 `--anthropic`、`--openai`、`--responses`、`--gemini`、`--systemone` 之一 |
| 路由取值为空、`/` 或 `///` | 用法错误：这条路由缺路径，写入不发生 |
| 有相对路径却没给 `--base-url` | 整次写入被拒，并指出是哪条路由或 `--models-path` 少了地址 |
| `--base-url` 只有 scheme，或 scheme 不是 http(s) | 用法错误 |
| `--default-protocol` 不在本次声明的路由里 | 整笔拒绝，并列出这次声明了哪些协议 |

所有拒绝都发生在写库之前，不会留下半条记录。用法错误退出码为 2，其余为 1，见[退出码](/docs/cli#退出码)。

## gemini 的路径占位符

gemini 将模型名置于 URL 路径中，因此其路由支持 `{model}` 占位符：

```bash
lax provider add gem-proxy --base-url https://gemini-proxy.example.com \
    --gemini /v1beta/models/{model}:generateContent \
    --default-protocol gemini
```

占位符按原样入库，在发起请求前替换为模型名（含 `/` 的名称按路径段转义）。相对路径与完整地址两种写法均支持占位符。替换只发生在发请求那一刻，库里存的仍是 `{model}`。因此同一条路由能接所有模型：

| 客户端请求的模型 | 上游实际收到的地址 |
| --- | --- |
| `gemini-2.5-pro` | `https://gemini-proxy.example.com/v1beta/models/gemini-2.5-pro:generateContent` |
| `gemini-2.5-flash` | `https://gemini-proxy.example.com/v1beta/models/gemini-2.5-flash:generateContent` |
| `org/gemini-pro`（名字带 `/`） | `https://gemini-proxy.example.com/v1beta/models/org%2Fgemini-pro:generateContent` |
| `gemini-2.5-pro`，流式 | `https://gemini-proxy.example.com/v1beta/models/gemini-2.5-pro:streamGenerateContent?alt=sse` |

## 接入决策模型（systemone）

systemone 是决策协议：一次请求给一份材料与一组问题，返回每个问题的答案与概率，不出文本，也不参与协议转换（协议细节见[决策请求](/docs/gateway/decision)）。TypeSafe 的完整接入如下：

```bash
lax provider add typesafe --base-url https://api.typesafe.ai \
    --systemone /v1/systemone \
    --models-path /v1/models \
    --default-protocol systemone
lax account add ts1 --provider typesafe      # 凭据走 --key、标准输入或 LAX_KEY
lax model sync ts1
lax model probe ts1
lax decide --model jev-latest --state '付款失败三天，损失在扩大，请今天处理' \
    --noul urgent='是否要求今天处理'
```

三个参数各有原因：

| 参数 | 取值 | 不填时 |
| --- | --- | --- |
| `--systemone` | `/v1/systemone` | 这家没有 systemone 路由，模型算不出 systemone 出站协议，决策请求会按对话协议发出去并换回 400 |
| `--models-path` | `/v1/models` | systemone 路由不推导清单地址（与 openai-chat 不同），这家又没有别的路由可借，`model sync` 取不到地址 |
| `--default-protocol` | `systemone` | 默认协议的回退顺序不含 systemone，`provider ls` 与 `account ls` 的协议列显示 `-`，模型探出协议之前转发算不出出站协议 |

commandcode 的 Provider API 也提供决策模型，它的 base URL 已含 `/provider/v1`，路由写相对路径即可：

```bash
lax provider set commandcode --systemone /systemone
lax account add cc1 --provider commandcode --key sk-xxx --models typesafe/jev
lax model probe --account cc1 --model typesafe/jev
```

它的清单不列决策模型，所以 `typesafe/jev` 要用手填的 `--models` 写进模型目录；写完还要跑一次 `model probe`，把该模型的协议探出来。
