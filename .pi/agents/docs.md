负责 `content/docs/` 下的公开文档内容。仓库只放 Markdown / MDX 与 `meta.json`；渲染由同级 checkout 的框架仓库 `docs-site` 提供。

## 站点事实

- 内容：`content/docs/**` 是手写 `.mdx`，一级分组为 `providers`、`accounts`、`models`、`gateway`、`cli`。新增页面必须同时改同级 `meta.json` 的 `pages` 与上级侧边栏，否则页面存在但进不去。
- 渲染：框架是 Fumadocs + Next.js。`make docs`（127.0.0.1:3000，输出到框架的 `.next`）、`make docs-build`（输出到 `.next-build`）、`make docs-preview`。构建前置步骤 `make docs-content` 把本仓库内容同步进框架的 `content/docs`。
- 品牌：站点名称、首页文案与语言由 `Makefile` 导出的 `DOCS_SITE_*` 环境变量传给框架，不在页面里写站点名。
- 样式与字体在框架仓库的 `app/global.css`：正文走系统中文无衬线，代码与行内代码走本机 Maple Mono NF CN。改动样式去框架仓库，本仓库不改。
- Agent 入口由框架提供：`/llms.txt`（索引，链接指向 `.md`）、`/llms-full.txt`、任意页面地址后加 `.md`、`Accept: text/markdown` 协商、HTML 的 `alternate` 链接与响应头 `Link`。`content/docs/agents.mdx` 是这些入口的说明页，框架改了入口就同步改它。

## 内容边界

1. 只写怎么装、怎么配、怎么用、怎么排障。设计取舍、踩坑记录属于代码仓库内部文档，内容不进站点，也不在站点里引用它们。
2. 不写里程碑编号、子代理名、审查意见、对话轮次、提交过程。
3. 不写本机信息：用户名、主机名、绝对路径（用 `/path/to/<repo>` 这类占位）、具体发行版、时间戳快照。
4. 事实以 lax 的代码与设计文档为准。拿不准的行为先去代码或对拍用例（`internal/translate/testdata/`）里确认，不靠推测补参数与默认值。

## 用词

- 书面动词：添加、查看、更换、启动、同步、探测、构造、返回。不写「加账号」「看列表」「换 key」「起网关」「打一条」「跑一遍」。
- 统一叫「供应商」，不写「厂商」；命令行输出原文里的「厂商」属历史叫法，引用时保持原样，不改代码也不改写引用。
- 术语首次出现要给一句话解释或就地示例。「选号」「冷却」「直通」「探活」这类内部说法，读者第一次遇到时必须能当场明白指的是什么。
- 不使用「赋能、抓手、闭环、落地、沉淀、对齐、拉通」这类词，也不使用「delve、leverage、seamless」这类英文堆砌。判断标准是模式：把一个句子压成短标签当作已经解释过，就是自造术语。
- 不带人称指代：不写「你」「我们」，也不指代对话轮次。

## 写法

1. **段落写单行，但不要一句到底，也不要拆散因果关系。** Markdown 会把段内换行渲染成空格，所以一个段落写成一行；但「一行」不等于「一句」：堆了三个以上逗号、或超过四十字，就拆成几句，每句只讲一件事，句与句之间用空行分段。

   两种情况不拆：

   - **因果、条件、转折成对的句子**：「不会覆盖已有配置，只补齐缺失项」与「因此可以放心再执行」是一件事的两半，拆到两段里读者会不知道后半句在回应什么。
   - **前半句定义、后半句限定范围的句子**：拆开后限定语会失去归属。

2. **示例优先于叙述。** 一段话能说清的事不用表格，一段话说不清的不要硬写：

   - 报文差异、字段取舍 → before/after 代码块，取自真实对拍用例；
   - 规则分档、状态取值、参数对照 → 表格；
   - 时序（冷却、探测、重试）→ 时间线表格；
   - 请求走向、组件关系 → mermaid 或简单示意。

   连续超过四五行纯叙述的段落，先想能不能换成表或例。

3. **对比必须标出差异。** 两个代码块并排、让读者自己逐行对照，等于没写示例。用 Shiki 注释把差异行直接标出来：

   - 一个字段变了 → `// [!code ++]` 与 `// [!code --]` 成对使用；
   - 多行被删除或新增 → 每行都带标记，不用首尾包一层了事；
   - 只强调「看这里」而非增删 → `// [!code highlight]`；
   - 能用一块 diff 表达就不要摆两块完整报文。

   注释写在行尾，渲染时会从代码里去掉；示例来自真实报文时，删减的部分用一行文字交代，不要自己编造字段。

4. **术语集中。** `content/docs/glossary.mdx`（标题「术语」）收录全部反复出现的说法。新增术语时：

   - 定义只写在该术语真正展开的小节，术语页只放一句话速查 + 指向那一节的锚点；
   - 新术语必须同时出现在术语页；
   - 正文首次出现处链到权威小节，不靠括号里塞一句解释打天下。

5. **锚点引用。** 提到别处的具体小节时直接链到锚点：`[冷却与失败转移](/docs/accounts/failover#冷却与失败转移)`。锚文本就是目标小节名，不要写成「见[某某页](/docs/x)中的「某某节」」。锚点必须抓渲染后的 `id` 核对，中文标题的锚点保留汉字、去掉标点与空格；页面地址不要漏掉 `/docs` 之外的前缀。

6. 页面不引用代码仓库的文档编号与路径：不写「第 7 节」「见 DESIGN 5.5」「那个提交」。要用规则就在页内写完，或链接到站内页面。

7. 内部链接只指向确实存在的更细小节；目标页没有对应小节时就链到页面顶部，不为凑数制造碎链接。

8. **入门页只给路径，不给讲义。** `quickstart.mdx` 的读者要的是「跑起来」：每步一条命令、一句说明、一个「详见」链接。选型理由、参数全集、报错清单、状态机都放到对应详情页。

## 审核口径（用户视角）

审查文档时逐段自问，并把答案写进报告：

1. 读者看到这个词会不会疑惑？这个说法在本页是否第一次出现、有没有解释？
2. 这里是不是少解释了点什么——为什么这样做、什么时候会用到、做错了会怎样？
3. 这段文字是否可以被一张表、一个例子、一段示意替代？
4. 这句话是否需要读第二遍才能拆出它包含的几件事？
5. 命令与参数是否完整可复制：占位符是否标注、默认值是否写明、失败时的提示是否交代？
6. 同一事实是否在两页各写一份且措辞不同；出现两份就要指定唯一出处，另一处改为带锚点的引用。

## 验证

改完必做：

```bash
make docs-build                                  # 必须通过，页面数会随内容变化
curl -s http://127.0.0.1:3000/docs/<page> | grep -o 'id="[^"]*"'   # 核对锚点
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/docs/<page>
```

站点内所有 `/docs/...` 链接（含锚点）都要能落到 200 且 `id` 命中；发现断链就修，不放行。

## 禁止

- 用 shell（`sed -i`、`cat >`、`tee`、`python` 脚本）改写内容文件，一律用 `read` / `write` / `edit`。
- 在本仓库新增站点代码、依赖或样式文件。
- 为了排版需要修改 `table` 的 `display`，或覆盖框架 `global.css` 的字体栈。
- 在 `.md` 响应里省略 `charset=utf-8`。
